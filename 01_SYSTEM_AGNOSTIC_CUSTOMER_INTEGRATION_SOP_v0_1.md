# System-Agnostic Customer Governance Integration SOP

Version: v0.1.1

Release: Public

## 1. Purpose

This SOP defines a reusable integration procedure for connecting an existing customer system to a governance system and a read-only governance observation surface.

The SOP is intentionally independent of any single product, database schema, API shape, programming language, runtime topology, storage model, or visualization design.

The integration target is a semantic and authority boundary, not a physical copy of a reference implementation.

## 2. Universal integration roles

Every customer integration shall identify the following logical roles as applicable:

- `CUSTOMER_SYSTEM`: the customer's existing system or application.
- `CUSTOMER_SOURCE`: the customer-controlled source of factual runtime or business information.
- `GOVERNANCE_INPUT`: the normalized facts admitted to governance processing.
- `AUTHORITY_BOUNDARY`: the rule separating customer facts from governance-derived or governance-generated state.
- `INTEGRATION_ADAPTER`: the mapping layer between customer-native representations and governance semantic roles.
- `EVIDENCE_SURFACE`: the persisted or reproducible evidence required for audit and replay.
- `OBSERVATION_INTERFACE`: a read-only surface for viewing governance state, evidence, or trajectory.

These are logical roles. They do not prescribe file names, table names, API paths, event names, or implementation technology.

## 3. Core principles

### 3.1 Semantic mapping, not schema copying

Customer-native fields, events, records, APIs, streams, or equivalent representations are mapped to semantic roles.

A customer is not required to reproduce reference field names.

### 3.2 Explicit authority separation

Customer-supplied information remains customer fact authority.

The customer does not gain authority to assert governance-derived state or governance-generated evidence merely by supplying similarly named values.

### 3.3 Capability-scoped requiredness

A semantic role is required only when:

1. the selected governance capability uses that role; and
2. the Customer Input Mapping Contract declares that role applicable.

Reference role counts are examples, not universal minimum field counts.

### 3.4 Optional inputs remain optional

Optional customer information may be bound when useful.

Its absence must not be silently converted into governance authority or into an undocumented required field.

### 3.5 Governance derivation remains governance-owned

Governance-derived decisions, classifications, signals, continuity judgments, drift judgments, or equivalent states are computed by the governance layer.

They are not customer-provided authoritative inputs.

### 3.6 Governance-generated artifacts remain governance-owned

Audit records, evidence records, receipts, reports, hashes, replay links, explanations, and equivalent artifacts are generated by the governance layer when the selected implementation requires them.

### 3.7 Observation is read-only

The observation interface may display governance-derived or governance-generated state but must not become an alternate write path into governance authority.

### 3.8 Reference visualization is not universal architecture

A reference implementation may use a particular set of observation dimensions.

A customer implementation may use any capability-appropriate observation model that preserves the same authority and evidence boundaries.

## 4. Integration procedure

### Step 1 — Define the customer integration boundary

Document:

- the customer system being integrated;
- the governance capabilities being requested;
- the customer-controlled sources that may provide factual inputs;
- the intended observation interface;
- the evidence and replay requirements;
- the authority boundary.

Do not select physical customer fields merely because their names resemble reference fields.

### Step 2 — Select applicable semantic roles

Use the Customer Input Mapping Contract as a role catalog.

For each selected governance capability:

1. identify the semantic roles needed by that capability;
2. mark whether each role is applicable;
3. classify the role as customer-required, customer-optional, governance-derived, or governance-generated;
4. do not infer requiredness from the reference implementation's row count.

### Step 3 — Bind customer-native sources

For every applicable customer-side role, record:

- customer field or equivalent representation;
- customer source;
- transform, if any;
- provenance;
- cardinality or multiplicity required by the customer implementation;
- applicability condition;
- explicit fallback policy, if allowed.

The mapping may target database fields, API properties, event payloads, log records, state objects, streams, or another stable customer-native representation.

### Step 4 — Validate responsibility ownership

Apply the four base responsibility classes:

- `CUSTOMER_REQUIRED`
- `CUSTOMER_OPTIONAL`
- `GOVERNANCE_DERIVED`
- `GOVERNANCE_GENERATED`

Do not create additional base classes merely to represent applicability, lifecycle conditions, fallback behavior, or cardinality.

Those are separate contract dimensions.

### Step 5 — Validate source and provenance

For each bound customer-side role:

1. verify that the source belongs to the declared customer authority boundary;
2. document any transform;
3. preserve provenance sufficient to determine where the fact came from;
4. reject mappings whose source or transformation cannot be traced.

### Step 6 — Build the integration adapter

The integration adapter shall:

- read customer facts from declared customer sources;
- map them into semantic governance inputs;
- preserve the customer fact/governance authority distinction;
- avoid giving customer metadata authority over governance-derived fields;
- fail or hold when an applicable required role is unavailable;
- preserve optionality when an optional role is unavailable.

The adapter does not need to use the same language, class structure, directory layout, or storage mechanism as the reference implementation.

### Step 7 — Bind governance outputs

Governance-derived and governance-generated roles are bound to the governance implementation's output and evidence surfaces.

The customer may consume these outputs but may not supply them as authoritative governance state.

### Step 8 — Connect a read-only observation interface

The observation layer may visualize:

- governance state;
- decisions;
- continuity;
- divergence;
- drift;
- evidence linkage;
- audit history;
- trajectory;
- other capability-specific governance observations.

The selected observation dimensions are implementation-defined.

The observation interface must not modify governance authority.

#### Step 8.1 — Return an observation locator

For each accepted observable execution or observation session, the integration shall return or expose an implementation-defined execution identity and a read-only observation locator bound to that same execution or session.

The customer or user must not be required to discover internal storage paths, search evidence bundles, guess an identifier, or infer the observation target from unrelated runtime data.

The locator may be a URL, opaque identifier, signed reference, API resource, or equivalent implementation-defined handle.

The supported user flow shall ensure that:

- the execution or session identity is returned to the caller or otherwise surfaced to the user;
- the observation locator resolves unambiguously to that same execution or session;
- locator resolution remains read-only and grants no governance or execution authority;
- internal write credentials, secrets, and authorization tokens are not required in the observation locator;
- when no valid observation locator can be produced, the integration reports observation unavailable rather than substituting or guessing another execution.

### Step 9 — Run acceptance gates

Execute the acceptance requirements defined in `04_ACCEPTANCE_AND_VERIFICATION_GATES_v0_1.md`.

A failed authority, provenance, mapping, fallback, portability, or observation-handoff gate blocks formal integration close.

### Step 10 — Seal the customer integration package

The customer-specific integration package should include:

- completed Customer Input Mapping Contract;
- declared governance capabilities;
- responsibility classifications;
- source/provenance bindings;
- transform declarations;
- applicability and fallback rules;
- acceptance evidence;
- integration adapter identity/version;
- evidence and replay references;
- execution/session identity and observation-locator handoff evidence;
- final acceptance result.

## 5. Customer-specific completion rule

This generic SOP is complete without customer-specific field bindings.

A concrete customer deployment is not complete until its own selected semantic roles have been bound to customer-native sources and have passed the acceptance gates.

## 6. Prohibited shortcuts

Do not:

- copy reference field names and call that a customer contract;
- treat a reference path as a customer requirement;
- require the reference implementation's exact role count;
- require a reference visualization's exact axes;
- allow customer inputs to self-authorize governance state;
- allow the observation UI to write governance authority;
- infer provenance from field names;
- silently promote an optional input to required;
- silently use fallback without contract authorization;
- require the user to search internal evidence or guess an observation-session identifier;
- close the integration when applicable required mappings are unresolved.

## 7. Completion criterion

A customer integration is ready for formal close only when:

1. the selected capability set is explicit;
2. every applicable required customer role is bound;
3. optional roles are explicitly handled;
4. all bindings have source and provenance;
5. transforms are declared;
6. the four-class responsibility boundary is preserved;
7. governance-derived and governance-generated outputs remain governance-owned;
8. observation remains read-only;
9. each accepted observable execution exposes an execution/session identity and a read-only observation locator bound to that same execution;
10. acceptance gates pass;
11. the customer-specific evidence package is sealed.
