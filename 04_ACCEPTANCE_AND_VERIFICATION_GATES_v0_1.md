# Acceptance and Verification Gates

Version: v0.1.2

Release: Public

## 1. Purpose

These gates determine whether a concrete customer integration may be formally accepted.

All applicable gates must pass.

## 2. Acceptance gates

| ID | Scope | Requirement | Pass condition | Failure boundary |

## 3. Formal close rule

A customer integration must not be formally closed while any applicable acceptance gate is failed or unresolved.

## 4. Minimum evidence

Acceptance evidence should identify:

- customer mapping contract version;
- integration adapter version;
- governance capability set;
- input source/provenance evidence;
- applicable fallback declarations;
- governance output/evidence identity;
- governance-system generation and ownership evidence for the canonical long-term governance identity;
- governance session identity and ordered successor-chain evidence;
- read-only Control Room locator binding evidence;
- evidence that session rotation and successor append preserve the same long-term governance identity and Control Room locator;
- evidence that the customer-facing Control Room locator contains or requires no write credential;
- initial customer handoff evidence showing the long-term governance identity and stable Control Room URL;
- evidence that the customer was explicitly instructed to save or retain the long-term governance identity and Control Room URL;
- prior-session and prior-event preservation evidence after successor append;
- preservation evidence for any recorded partial session without a valid trajectory point;
- trajectory-to-session linkage and ordered cross-session trajectory evidence when valid trajectory points exist;
- gate-by-gate result;
- final sealed acceptance result.
